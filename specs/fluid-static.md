# fluid-static

## 1. Role

The static API translates an application-supplied `ContainerSchema` into an Aqueduct runtime registry, creates a root datastore containing handles to initial objects, and wraps the loader container and audience. Schema is **code supplied again on load**, not a serialized class manifest. (reference/fluidframework-3.11.0/packages/framework/fluid-static/src/rootDataObject.ts:191-224, reference/fluidframework-3.11.0/packages/framework/fluid-static/src/types.ts:62-94.)

## 2. Surface used by other packages

`ContainerSchema = {initialObjects:Record<string,SharedObjectKind>,dynamicObjectTypes?:readonly SharedObjectKind[]}`. Kind is a DDS factory provider or a DataObject factory provider; initial keys become API property names. Runtime construction: `createDOProviderContainerRuntimeFactory({schema,oldestSupportedClient,rootDataStoreRegistry?,runtimeOptionOverrides?})`; optional registry replaces the derived nested datastore registry, not the DDS registry. `createFluidContainer({container})` resolves `IStaticEntryPoint`; `createServiceAudience({container,createServiceMember})` adapts users. The wrapper exposes `initialObjects,connectionState,isDirty,disposed,attachState,attach,connect,disconnect,create,dispose`, internally `container,acquireExtension,uploadBlob`. (reference/fluidframework-3.11.0/packages/framework/fluid-static/src/types.ts:43-94, reference/fluidframework-3.11.0/packages/framework/fluid-static/src/rootDataObject.ts:191-224, reference/fluidframework-3.11.0/packages/framework/fluid-static/src/fluidContainer.ts:122-293.)

## 3. Wire and persisted formats

### Directory-root layout: exact identities

| Meaning | Literal / rule |
|---|---|
| Container registry entry | `["rootDO",Promise.resolve(rootFactory)]` |
| Root datastore package path | `["rootDO"]` |
| Root datastore alias | `"rootDOId"` (not its physical ID) |
| Root DDS channel ID | `"root"` |
| Root DDS factory type | `"https://graph.microsoft.com/types/directory"`, snapshot version `"0.1"` |
| Directory under root | `"initial-objects-key"` |
| Each initial-object entry | schema key → object **handle**, not object value/class/type |
| DDS initial-object channel | runtime-generated channel ID (`createChannel(undefined,type)`), owned by root datastore |
| DataObject initial object | new datastore with package path `["rootDO",factory.type]`, runtime-generated datastore ID |

These identities are chosen by root construction, Aqueduct initialization and kind creation respectively. A key such as `map` is **not** the channel ID. Dynamic types register factories but create no objects or entries. Nested data stores may themselves register deeper packages. (reference/fluidframework-3.11.0/packages/framework/fluid-static/src/rootDataObject.ts:76-112, reference/fluidframework-3.11.0/packages/framework/fluid-static/src/rootDataObject.ts:158-177, reference/fluidframework-3.11.0/packages/framework/fluid-static/src/rootDataObject.ts:265-309, reference/fluidframework-3.11.0/packages/framework/fluid-static/src/utils.ts:74-129, reference/fluidframework-3.11.0/packages/framework/aqueduct/src/data-objects/dataObject.ts:31-77, reference/fluidframework-3.11.0/packages/dds/map/src/directoryFactory.ts:32-40.)

Concrete example for schema `{initialObjects:{map:SharedMap,child:ExampleDO},dynamicObjectTypes:[SharedCounter]}` where `ExampleDO.factory.type="example"`: container registry is `rootDO`; its child registry contains `example`; its channel registry contains the map and counter factories plus Aqueduct directory/map defaults. Given generated datastore IDs `R` and `D` and channel ID `C`, alias summary blob `.aliases` contains `[["rootDOId","R"]]`; R's `.component` JSON is `{"pkg":"[\"rootDO\"]","summaryFormatVersion":2,"isRootDataStore":true}`; D's package string is `"[\"rootDO\",\"example\"]"`. R/root's subdirectory `initial-objects-key` stores `map → /R/C` and `child → /D` as Fluid handles (serialized handle object `{"type":"__fluid_handle__","url":"/R/C"}` inside the directory value serializer), **not** `/rootDOId/map`. Alias tuples and `.component` strings are runtime-owned persisted data; schema/kind constructors are not persisted. (reference/fluidframework-3.11.0/packages/framework/fluid-static/src/utils.ts:109-129, reference/fluidframework-3.11.0/packages/framework/aqueduct/src/data-object-factories/pureDataObjectFactory.ts:410-429, reference/fluidframework-3.11.0/packages/runtime/container-runtime/src/containerRuntime.ts:2948-2950, reference/fluidframework-3.11.0/packages/runtime/container-runtime/src/dataStoreContext.ts:109-125, reference/fluidframework-3.11.0/packages/runtime/container-runtime/src/summary/summaryFormat.ts:214-242.)


For that detached example, assuming no client ID yet and both handles small, the `root` channel's `header` blob string is literally:

```json
{"blobs":[],"content":{"ci":{"csn":0,"ccIds":[]},"subdirectories":{"initial-objects-key":{"ci":{"csn":0,"ccIds":["detached"]},"storage":{"map":{"type":"Plain","value":{"type":"__fluid_handle__","url":"/R/C"}},"child":{"type":"Plain","value":{"type":"__fluid_handle__","url":"/D"}}}}}}}
```

Here map creation was assumed to resolve before child creation; reversed completion reverses storage insertion order. Directory emission inserts `ci`, then optional `storage`, then optional `subdirectories`; wrapper inserts `blobs`, then `content`. Values >=8192 UTF-16 code units in their serialized JSON move into `blob0`, `blob1`, etc., with their directory path repeated as nested `subdirectories`, and names listed in header.blobs; header.content retains directory creation metadata. Loading recognizes new format by Array.isArray(blobs), populates content then extra blobs in list order; otherwise treats entire header as the old bare directory object. Legacy `type:"Shared",value:"/path"` migrates to Plain with a Fluid handle. (reference/fluidframework-3.11.0/packages/dds/map/src/directory.ts:429-437, reference/fluidframework-3.11.0/packages/dds/map/src/directory.ts:691-706, reference/fluidframework-3.11.0/packages/dds/map/src/directory.ts:1001-1066, reference/fluidframework-3.11.0/packages/dds/map/src/directory.ts:1280-1296, reference/fluidframework-3.11.0/packages/dds/map/src/directory.ts:2361-2367, reference/fluidframework-3.11.0/packages/dds/map/src/localValues.ts:35-68.)

The concrete example's channel registry wire keys are `https://graph.microsoft.com/types/map`, `https://graph.microsoft.com/types/counter`, `https://graph.microsoft.com/types/directory`; the nested datastore registry key is application-chosen `example`. Tree root's channel registry uses `https://graph.microsoft.com/types/tree`. No schema-key-to-type table is persisted in initial-objects-key; those entries are only handles. (reference/fluidframework-3.11.0/packages/dds/map/src/mapFactory.ts:32-40, reference/fluidframework-3.11.0/packages/dds/counter/src/counterFactory.ts:30-38, reference/fluidframework-3.11.0/packages/dds/map/src/directoryFactory.ts:32-40, reference/fluidframework-3.11.0/packages/dds/tree/src/sharedTreeAttributes.ts:18-18, reference/fluidframework-3.11.0/packages/framework/fluid-static/src/rootDataObject.ts:102-107.)

The public tree-root alternative is **different**, not automatic: `createTreeContainerRuntimeFactory` registers `treeRootDO`, aliases `treeRootDOId`, and uses a `root-tree` SharedTree channel; `initialObjects` always returns `{tree:this.tree}`. Both service clients in this assignment explicitly select the directory-root factory, even for a schema with only `{tree:SharedTree}`. `isTreeContainerSchema` only recognizes exactly one initial key `tree` of SharedTree factory type; it does not switch the service clients' construction path. (reference/fluidframework-3.11.0/packages/framework/fluid-static/src/treeRootDataObject.ts:77-125, reference/fluidframework-3.11.0/packages/framework/fluid-static/src/treeRootDataObject.ts:143-188, reference/fluidframework-3.11.0/packages/framework/aqueduct/src/data-objects/treeDataObject.ts:17-110, reference/fluidframework-3.11.0/packages/framework/fluid-static/src/utils.ts:147-168, reference/fluidframework-3.11.0/packages/service-clients/tinylicious-client/src/TinyliciousClient.ts:173-176, reference/fluidframework-3.11.0/packages/service-clients/azure-client/src/AzureClient.ts:320-328.)

## 4. Behavior

### Registry and root initialization transitions

1. Enumerate `Object.values(initialObjects)` then `dynamicObjectTypes ?? []`; deduplicate kind objects by identity in a Set. DDS kinds contribute `getFactory()` to a Set; DataObject kinds contribute fresh `[type,Promise.resolve(factory)]` tuples. Reject an empty combined registry.
2. Construct root factory with type `rootDO`; install nested registry. Container runtime options begin `{enableRuntimeIdCompressor:"on"}` then caller overrides; oldest-supported version is passed through (the defaults function currently ignores its version argument).
3. New container: create detached datastore `["rootDO"]`; initialize it fully before attaching its runtime; `trySetAlias("rootDOId")`. Non-Success retrieves and returns the already-aliased object's handle target instead of returning the candidate.
4. New root DataObject first creates/binds `root` SharedDirectory. Its first-time hook creates `initial-objects-key`; starts one asynchronous creation per `Object.entries(initialObjects)` entry and sets each entry to its handle **as creation finishes**; awaits all.
5. Every initialization: enumerate stored directory entries (not the current schema keys), start `value.get()` for each; assign each resolved object into `_initialObjects` on completion; await all. `initialObjects` throws if its result has zero own keys, including an empty initial schema with nonempty dynamic types.
6. Entry point resolves alias `rootDOId`, gets its object, requires `.RootDataObject`, then returns `{rootDataObject,extensionStore}` with a nonenumerable self-provider `IStaticEntryPoint`. No first-time hook runs on an existing root.

(reference/fluidframework-3.11.0/packages/framework/fluid-static/src/utils.ts:40-103, reference/fluidframework-3.11.0/packages/framework/fluid-static/src/compatibilityConfiguration.ts:18-37, reference/fluidframework-3.11.0/packages/framework/fluid-static/src/rootDataObject.ts:97-177, reference/fluidframework-3.11.0/packages/framework/aqueduct/src/data-object-factories/pureDataObjectFactory.ts:410-429, reference/fluidframework-3.11.0/packages/framework/fluid-static/src/utils.ts:136-140.)

### Wrapper state and event transitions

This layer has **no independent connection state**: getters read the underlying loader synchronously. Construction registers forwarding listeners in order `connected,closed,disconnected,saved,dirty`. Underlying `closed(error?)` synchronously emits wrapper `disposed(error?)`; underlying `connected/disconnected/saved/dirty` synchronously emit their same-named wrapper event with **no arguments**. There is no replay for events occurring before wrapper construction, and no wrapper `attached` event. `disposed` means loader `closed`, not loader `disposed`. (reference/fluidframework-3.11.0/packages/framework/fluid-static/src/fluidContainer.ts:322-361.)

`connect()` and `disconnect()` call optional loader methods immediately, then return an async-resolved Promise; they do not await a connected/disconnected event. Default `attach`: if state != Detached reject `Cannot attach container. Container is not in detached state.`; otherwise reject `Cannot attach container. Attach method not provided.` Service clients replace this function only for newly-created containers. `dispose`: call `container.close()` **first** (so its closed→disposed forwarding still runs), then unregister the five forwarding listeners in registration order. `create(kind)` and blob upload delegate to the root. No state deduplication or additional wrapper event scheduling is introduced. (reference/fluidframework-3.11.0/packages/framework/fluid-static/src/fluidContainer.ts:376-407.)


Underlying loader boundary rules visible through this wrapper: connect rejects closed (`The Container is closed and cannot be connected`) or not Attached (`The Container is not attached and cannot be connected`); attached and already connected is a no-op, otherwise enables autoreconnect then resumes queues/connection. disconnect rejects closed, otherwise disables autoreconnect. On Connected, loader sets protocol-audience self, then signal-audience self, then runtime connection status, then protocol connection status, then raises connected (wrapper removes its clientId argument). On CatchingUp it only sets signal-audience self and runtime status; no connected/disconnected wrapper event is emitted for intermediate states. (reference/fluidframework-3.11.0/packages/loader/container-loader/src/container.ts:1389-1434, reference/fluidframework-3.11.0/packages/loader/container-loader/src/container.ts:2211-2250.)

Loader attach state assignment precedes runtime.setAttachState and underlying attaching/attached event; wrapper does not forward these, so observe attachState getter or await attach. On close, delta manager marks closed, disposes connection (disconnect propagation first), clears queues, emits closed; container closeCore closes protocol/runtime then emits closed(error), mapping synchronously to disposed(error). Container lifecycle is still closing during that callback, changed to closed in finally afterward. Repeated delta-manager close is no-op. With the legacy dirty callback, going dirty sets both dirty/pending before dirty event; going clean clears pending first (which may synchronously raise connected), then emits saved only if no reentrant op restored pending. Separate pending-state runtimes update public dirty independently and emit only on dirty-state change. Consequently **connected may precede saved**, and saved must be suppressed if connected listeners create an op. (reference/fluidframework-3.11.0/packages/loader/container-loader/src/container.ts:1279-1292, reference/fluidframework-3.11.0/packages/loader/container-loader/src/deltaManager.ts:789-797, reference/fluidframework-3.11.0/packages/loader/container-loader/src/container.ts:1075-1122, reference/fluidframework-3.11.0/packages/loader/container-loader/src/container.ts:2513-2559.)

### Service audience

Only `details.capabilities.interactive` clients participate. `getMembers()` builds a fresh Map keyed by `user.id` in audience iteration order, using the first encountered connection's service-member fields, pushing `{id:clientId,mode:"read"|"write"}` for every included connection. It also replaces `lastMembers`, a map **by connection ID**, each value referencing that user's aggregate. Initial constructor calls `getMembers()` to seed this cache. Add event for an interactive client calls `getMember` (which refreshes aggregation), emits `memberAdded(clientId,aggregate)`, then `membersChanged()`. Removal emits `memberRemoved(clientId,lastMembers.get(clientId))` and then `membersChanged` **only when the cached map contains that connection**; it does not recompute or delete the cache itself. Connected emits `membersChanged`; no disconnected forwarding exists here. `getMyself` uses `container.clientId`; absent ID/member returns undefined, otherwise `{...member,currentConnection:clientId}`. A noninteractive self present in raw audience can instead trigger the getMember missing-user error. (reference/fluidframework-3.11.0/packages/framework/fluid-static/src/serviceAudience.ts:68-165.)

## 5. Invariants and asserts

`0xb9e`: container entry point provides `IStaticEntryPoint`; `0xb9f`: aliased object provides RootDataObject; tree equivalent `0xbe7`. Missing alias throws `default dataStore [rootDOId] must exist`; missing subdirectory throws `InitialObjects sub-directory was not initialized`; empty loaded objects throw `Initial Objects were not correctly initialized`. A kind must have exactly one of `getFactory` and a factory self-provider (`factory.IFluidDataStoreFactory === factory`), otherwise UsageError `Invalid LoadableObjectClass`. (reference/fluidframework-3.11.0/packages/framework/fluid-static/src/fluidContainer.ts:283-287, reference/fluidframework-3.11.0/packages/framework/fluid-static/src/rootDataObject.ts:83-88, reference/fluidframework-3.11.0/packages/framework/fluid-static/src/rootDataObject.ts:136-170, reference/fluidframework-3.11.0/packages/framework/fluid-static/src/utils.ts:40-55, reference/fluidframework-3.11.0/packages/framework/fluid-static/src/treeRootDataObject.ts:109-118.)

## 6. JS-semantics hazards

Keep alias, physical datastore ID, channel ID and schema key distinct. Preserve JS own-property ordering, Set identity semantics, async completion order of directory writes and object assignments, and synchronous nested event forwarding. Removal payload is a cached aggregate that may still contain the departing connection. Optional provider properties and nonenumerable self-provider are not persisted schema. (reference/fluidframework-3.11.0/packages/framework/fluid-static/src/rootDataObject.ts:97-140, reference/fluidframework-3.11.0/packages/framework/fluid-static/src/utils.ts:74-103, reference/fluidframework-3.11.0/packages/framework/fluid-static/src/utils.ts:136-140, reference/fluidframework-3.11.0/packages/framework/fluid-static/src/serviceAudience.ts:90-120.)
